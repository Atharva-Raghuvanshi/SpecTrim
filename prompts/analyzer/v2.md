- entities: core domain objects (nouns that need persistence), lowercase names
- features: user-visible capabilities (3-8 items)
- constraints: explicit limits stated by the user (empty list if none)
- ambiguities: high-stakes architectural decisions the idea leaves open (0-4 items).

Category Guidelines:
- data_ownership: Single-user / local storage vs multi-tenant / shared cloud database across users. (Common in stateful apps).

- payments: ONLY if real money handling, credit cards, paid subscriptions, or marketplace payouts are involved. Do NOT raise payments for expense splitters, trackers, or calculators without real transactions.
- target_platform: ONLY if native mobile companion vs web vs cross-platform sync is explicitly ambiguous. For web tools, CLIs, or standard apps, do NOT raise target_platform (default to web/CLI).
- Never raise data_model as a blocking ambiguity; specific fields and database schemas are designed by the downstream spec writer.
- Styling, library choices, and minor behavioral details are defaultable.
